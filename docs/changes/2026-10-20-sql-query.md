# 销售表查询失败与 MySQL 端口不一致

## 问题现象

查询销售表前 40 条记录时，第一步列举表名即返回 `[SQL_RETRY_EXHAUSTED]`，重新下发任务仍失败。

## 定位证据

- 本地配置指向 `localhost:3307`、`deepsearch_db`，单次实际连接返回 MySQL 错误码 2003、Windows 10061（连接被拒绝）。连接建立前已失败，尚未执行表名查询和销售查询。
- `docker ps -a` 显示 `deepsearch-mysql` 健康运行，端口映射为 `3306:3306`。
- 仅将诊断连接端口改为 3306 后，原有凭据、白名单及只读限制下，列举表名和销售表查询均成功。
- 因而本次根因是应用配置与容器实际映射端口不一致。不是 40 条结果过多；也没有证据表明跨任务重试预算未重置。最初两种可能仅为待验证假设。

## 解决方法与具体修改位置

- 本地 `.env`：`MYSQL_PORT` 从 3307 改为已验证的 3306。该文件继续保持 Git 忽略，不记录或提交密码。
- `app/tools/db_tools.py`：自动重试事件增加 MySQL 错误码和受控原因说明；重试耗尽时保留底层错误分类；预算耗尽后的再次调用仍显示原因。连接错误提示检查主机、端口、服务与容器映射，不直接输出可能包含查询数据的驱动原始异常。
- `tests/test_sql_safety.py`：增加连接错误 2003 的诊断保留与敏感异常内容不回显回归测试；验证最多首次执行加 3 次重试，预算耗尽后不再访问数据库。

## 验证结果

- `python -m unittest discover -s tests -p test_sql_safety.py`：16 项通过。
- 新进程读取修正后的 `.env`，实际调用 `list_sql_tables`：成功列出 `drugs`、`inventory`、`sales_records`。
- 同一重试作用域实际调用 `execute_sql_query`，执行 `SELECT * FROM sales_records ORDER BY sale_id LIMIT 40`：返回 40 条数据，重试计数 0。未在日志中记录业务记录内容。

## 限制与后续操作

- 本次未重启正在运行的 API/worker，也未进行浏览器模型对话验收。需重启后端；自动启动的 worker 随后端重新启动。手动运行的独立 worker 也需重启，避免继承旧环境。
- 此修复针对当前本机容器端口。其他部署须按实际映射配置 `MYSQL_PORT`，不应直接照抄本机端口。没有修改容器或数据库数据。
